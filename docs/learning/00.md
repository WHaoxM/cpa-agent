- 因此大量 block 被判定为“无文本”，最终 `document_blocks` 为空。

> 结论：当前阶段“解析引擎可用，归一化适配未完成”。

# NS-LE 架构重构阶段总结（2026-04-02）

## 1) 已完成的重构

### Stage 1: YOLOv10 版面检测集成
- **核心发现**: SmartResume 仓库自带 YOLOv10 ONNX 模型（265MB），之前完全未接入
- **模型规格**: Input [1,3,640,640] → Output [1,300,5]，格式为 **(cx, cy, w, h, score) normalized [0,1]**，单类检测
- **关键技术**: letterbox resize + ONNX Runtime 推理 + 坐标逆映射 + inter/intra-segment sorting
- **实际效果**: 在测试简历上检测到 5 个 layout regions，54 个 MinerU text blocks 成功对齐（仅 1 个未匹配）

### Stage 2: 物理解析层重构（修复 P0 Bug）
- **Bug 修复**: `physics_analysis.py` 的 `_extract_text()` 无法解析 MinerU v2 嵌套格式 → **physics_result.json 返回 0 个 block**
- **解决方案**: 将 `block_router.py` 的 `item_text()` 逻辑作为规范解析器，统一 v1/v2/middle.json 三种格式
- **BlockType 扩展**: 6 类 → 9 类（新增 JOB_TITLE/JOB_REQUIREMENTS/JOB_DESCRIPTION）
- **三层信号融合分类**: YOLOv10 layout region（强）→ MinerU title/level（中）→ heading 关键词（弱）
- **新增**: 跨页合并、JD TXT direct_text_loader、FallbackPolicy、Indexed Linearization

### Stage 3: 模块化重组
- `dictionaries/`: skill_lexicon（6大类）、pii_patterns（7类PII + 伦理敏感词）、entity_patterns（日期/学位/角色）
- `rules/`: privacy_rules（5种转换策略: TOKENIZE/DROP/GENERALIZE/PSEUDONYMIZE/HMAC）、logic_rules（约束矩阵）
- `prompts/`: resume_prompts（4个并行子任务）、jd_prompts（3个子任务）—— SmartResume 风格 Index-based Pointer

### Stage 4: 实体抽取识别层重构
- **Phase 2**: 严格按契约6步执行（伦理过滤→PII检测→PII转换→AC技能匹配→预标注→XML注入）
- **Phase 3**: 真实 Shannon Entropy（替代 hardcoded 0.8）、并行任务分解（ThreadPoolExecutor）、4阶段后处理
- **关键改进**: `apply_chat_template()` 替代裸 prompt 拼接，thinking mode 选择（复杂 /think，简单 /no_think）

## 2) 值得学习的关键技术点

### SmartResume 论文 (arXiv:2510.09722) 核心洞察
- **YOLOv10 不是做细粒度分类**，而是做 Layout Segments Identification（把多栏布局切成线性可读的区域）
- **Qwen3-0.6B 原始 F1=0.136，SFT 后 F1=0.838**（长文本）—— 微调是必须的
- **Index-based Pointer Mechanism**: LLM 返回行号范围而非生成全文 → 100% 内容保真 + 减少 token 消耗
- **JSON 输出不用 constrained decoding**，用 prompt 引导 + `text.find("{")` 后处理更稳定
- **后处理4阶段**: grounded re-extraction → domain normalization → context-aware dedup → source verification

### ONNX 模型调试经验
- YOLOv10 ONNX 输出格式不是标准的 (x1,y1,x2,y2,score)，而是 **(cx,cy,w,h,score) normalized**
- 判断方法: 如果某个 detection 的 y2 < y1，说明不是 xyxy 格式
- letterbox resize 的 padding 需要在坐标逆映射时减去

### 真实 Entropy 不确定性度量
- `model.generate(output_scores=True, return_dict_in_generate=True)` 获取每个 token 的 logits
- Shannon entropy: `-(probs * log2(probs)).sum()`
- Qwen3-0.6B vocab_size=151936, max theoretical entropy ≈ 17.2 bits，实际生成很少超过 12

# NS-LE v5.0 架构升级总结（2026-04-02）

## 1) 五个关键修复

### P0: OutputAdapter — Phase 3→4 Schema 断层
- **问题**: ReasoningCore 输出 task-specific JSON（`{"skills": [...]}`），LogicGuard 期望 `{"entities": [], "relations": []}`，导致 total_entities=0
- **方案**: 新增 `output_adapter.py`，将 task-specific KV 映射为契约格式，自动推导 relations
- **学术价值**: 这是 **Adapter Pattern** 在 NLP 管线中的经典应用，解耦了推理层和验证层

### P0: Section-Scope Inheritance + Entity-Name Heading Classification
- **问题**: MinerU v2 的二级标题是实体名（"四川轻化工大学"），不是章节标签（"教育经历"），导致 76.9% 分类覆盖率
- **方案**: 三级分类策略 — (1) 章节标签匹配 (2) 实体名标题分类（heading+content 双信号） (3) content-based fallback
- **关键洞察**: 中文简历的「标题层级 ≠ 语义层级」— 一级标题是 section label，二级标题是 entity name，但 MinerU 都标为 `title`

### P1: PII ADDRESS 正则负向先行断言
- **问题**: "省重点实验室" 被 ADDRESS 正则匹配并替换为 [ADDRESS_GENERALIZED]
- **方案**: `(?![\u4e00-\u9fa5]*(?:重点|建设|发展|级))` 排除非地址上下文

### P1: SkillMatcher 短词边界保护
- **问题**: "C"/"R" 单字符在 Learning/LangChain 中误匹配
- **方案**: 按长度分组 — 短词（<3字符）用带边界的正则，长词用 Aho-Corasick

### P2: Semantic Sub-splitting
- **问题**: 两个项目被 MinerU 合并到同一个 block（视觉间距不够大）
- **方案**: 检测 "角色+时间戳" 组合作为子块切割触发器

## 2) 论文级架构洞察

### SmartResume 对比
- SmartResume 论文（arXiv:2510.09722）**不做块分类**，直接全文送 LLM → 这规避了 heading classification 问题
- 但 SmartResume 需要 15,500 份 SFT 数据 → 标注成本过高
- NS-LE v5.0 的 **三级分类策略** 是 SmartResume 和传统规则引擎的中间态，更适合小团队

### ICLR 2025 gDSA vs 我们的方案
- gDSA 用 GNN 建模 6 种模态的层级关系 → 学术上更强
- NS-LE v5.0 的 entity-name heading classification 是 **纯规则 + 正则的轻量级替代**，不需要训练数据
- 但对于复杂多栏布局、创意简历，规则方案会退化，此时需要回退到 GNN 或 VLM

### 企业级关键决策（来自顾问委员会）
- **SFT 路线**: Teacher-Student Distillation — DeepSeek-V3/GPT-4o 生成金标数据 → 人工核对 → LoRA 微调 0.6B
- **架构核心原则**: LLM 只负责内容提取，不负责生成契约 JSON → OutputAdapter 做格式转接
- **竞赛杀手锏**: Dynamic Logic Guarding with Uncertainty Thresholding — 不确定性触发 Self-Correction Prompt

# 自主学习闭环 3-Phase 架构实现（2026-04-03）

## 1) 3-Phase 架构概览

```
Phase 1: 教师数据工厂 → Phase 1.5: 合成扩充 → Phase 2: 渐进式蒸馏 → Phase 3: 边缘自主推理 → 回流
```

### Phase 1: Teacher Data Factory
- **双轨提取**: 教师模型 API（DeepSeek/Gemini/Claude）+ NS-LE 规则引擎并行提取
- **ConsensusGuard**: 交叉共识质检，基于 entity span 集合交集计算一致性分数
- **分流**: consensus ≥ 0.8 → Gold | 0.4~0.8 → Silver | < 0.4 → Human Queue
- **Human-in-the-loop**: 冲突样本输出到 JSONL 文件，人工修正后调用 `approve_human_queue()` 提升为 Gold

### Phase 1.5: 合成数据生成（自动触发）
- **触发条件**: 每累积 5 份 Gold 数据自动触发
- **learn_patterns**: 教师模型分析 Gold 数据，提炼行业/技能/项目分布模式
- **generate_synthetic**: 基于学习到的模式 + 多样性参数批量生成合成简历
- **质量网关**: 合成数据必须通过 FieldConstraintValidator（score ≥ 0.6）才能进入 Silver 池

### Phase 2: Progressive Distillation
- **ReplayBuffer**: 经验回放池（500 cap），按 entity_type 分层采样，防灾难性遗忘
- **触发条件**: Gold + Silver ≥ 100 条
- **蒸馏**: 数据清洗 → 格式化 → Qwen3-0.6B LoRA SFT

### Phase 3: Edge Autonomous Inference
- **OODDetector**: 基于 embedding cosine distance 的分布外异常检测
- **路由**: confidence > 0.95 → 直接输出 | < 0.95 → 回流 Phase 1 教师标注

## 2) 关键技术点

### ReplayBuffer 经验回放
- **核心价值**: 解决持续学习中的灾难性遗忘（Catastrophic Forgetting）
- **三种采样策略**: uniform（均匀）、stratified（按 entity_type 分层）、difficulty（按难度加权，hard 3x 权重）
- **驱逐策略**: 容量满时优先移除 easy 样本，保留困难样本
- **企业级意义**: 这是 DeepMind 在 RL 中广泛使用的 Experience Replay 技术迁移到 NLP 蒸馏场景

### OOD 分布外检测
- **两种方案**: cosine distance（轻量 MVP）vs Mahalanobis distance（生产级）
- **cosine 方案**: 用 Gold 数据 embedding 计算质心，新样本与质心的余弦距离 → 映射到 [0,1] 置信度
- **mahalanobis 方案**: 考虑特征协方差矩阵，对高维空间中的异常分布更敏感
- **企业级意义**: 这是 Google BERT 论文组在 ACL 2020 提出的 OOD Detection for NLU 的简化实现

### FieldConstraintValidator 字段约束校验
- **6 条跨字段一致性规则**: CFR-001 ~ CFR-006
- **四维质量评分**: completeness(0.3) + consistency(0.3) + specificity(0.2) + chronology(0.2)
- **Gold/Silver/Reject 阈值**: 0.85 / 0.6 / < 0.6
- **企业级意义**: 类似 Great Expectations / Pydantic 的数据质量门禁，确保训练数据不引入噪声

### 教师模型模板标准化
- **4 个模板**: extract（解析）、annotate_ner（标注）、learn_patterns（学模式）、generate_synthetic（合成）
- **3 种 API 格式**: OpenAI-compatible / Anthropic / Gemini，一套模板兼容三种
- **温度策略**: 解析/标注用低温(0.1)保证精确，合成用高温(0.85)保证多样性

## 3) 新增文件
- `self_learning/resume_field_constraints.json` — 生产级字段约束 Schema
- `self_learning/teacher_model_templates.json` — 4 个教师模型 JSON 模板
- `self_learning/autonomous_loop.py` — 3-Phase 闭环控制器（AutonomousLearningLoop + ReplayBuffer + OODDetector）

# v2.1 隐患修复 — 专家评审驱动的三项架构补丁（2026-04-04）

## 评审原文核心论断
> "不要再去大改架构了，当前的首要任务是死磕 L0 层微调数据的纯净度，
> 以及跑通 L1 层 NetworkX 的第一批图谱节点。"

## 1) 隐患1: L1 静态骨架老化 → OOV Discovery Pipeline

### 问题
500个预定义技能节点是静态的，AI/前端领域半年内涌现大量新词（DeepSeek、Cursor、Vibe Coding）。
纯静态分类树会在6个月内过时。

### 解法: 新词发现管道
```
L0 skill_matcher → unmatched → oov_buffer.jsonl
  → Embedding近邻检测 (>0.85 alias / >0.70 related / <0.70 novel)
  → 频次聚合 (≥3% 审核 / ≥1% 观察 / <1% 丢弃)
  → LLM 自动归类 (valid? category? alias_of?)
  → taxonomy append-only 版本化更新
```

### 学习要点
- **Append-only更新**: 不修改骨架结构（6大类24子类不变），只增加叶子节点和别名
- **Blacklist**: 已判定为噪声的词永不再审核，防止重复消耗API
- **版本化**: v2.0→v2.1→v2.2，每次更新记录diff_log，可回滚
- **竞赛阶段可关闭**: 静态骨架对于竞赛数据已经够用

## 2) 隐患2: L4 长尾延迟 → Template-first + Streaming

### 问题
L0 层 1.22s 极速解析，L4 层 6次LLM串行/并行调用需 15-30s，用户体验头重脚轻。

### 解法: 70%模板直填 + 30% LLM 并行解读
```
Phase 1 (0ms): 结构化数据直接映射到报告字段
  ch1: 雷达图+基本信息 → 100%模板
  ch3: 匹配详情表 → 90%模板
  ch6: 评估指标 → 100%模板

Phase 2 (3-5s): 4次LLM并行, 只生成解读段落
  ch1 insight: 150-200字概括
  ch3 insight: 200-300字匹配解读
  ch4 insight: 150-200字方向建议
  ch5 insight: 200-300字学习寄语
  
总延迟: 3-5s (降低60-80%)
```

### 学习要点
- **Template-first 是企业级报告生成的标准做法**: 数据可视化部分不需要LLM
- **LLM的价值在"灵魂"不在"骨架"**: 只让LLM做它擅长的（洞察性结论、个性化建议）
- **SSE流式渲染**: 用户T=0s就能看到图表，LLM文本3-5s后流式插入
- **ch2行业趋势可缓存**: 同岗位的行业趋势不需要每次重新生成

## 3) 隐患3: L1/L3 冷启动数据荒 → Industry Common-sense Patch

### 问题
Jaccard计算严重依赖JD丰富度。初期几百份JD时，仅凭共享Git/VS Code就可能得出
"后端开发→UI设计"这种荒谬换岗路径。

### 解法: 行业常识亲缘矩阵 + 自适应权重
```
AFFINITY_MATRIX = {
  ("后端开发", "全栈开发"): 0.85,  // 高亲缘
  ("前端开发", "算法"):      0.15,  // 低亲缘
  ("产品",     "算法"):      0.05,  // 绝对否决
}

数据充足(≥20JD): combined = jaccard×0.8 + affinity×0.2
数据不足(<20JD): combined = jaccard×0.4 + affinity×0.6
硬约束: affinity < 0.15 → 绝对禁止
```

### 学习要点
- **行业先验≠偏见**: 在数据充足时affinity自然退化为软约束（0.2权重），不会限制真实的跨界转岗
- **PROMOTION_CHAINS作为兜底**: 即使0条JD也能输出有效的晋升图谱
- **data_confidence透明标注**: 每条边标明是"数据驱动"还是"模板补充"，评审可追溯
- **自适应权重平滑过渡**: 不需要手动切换模式，数据量增加时权重自动调整

# v3.0 自进化智能体升维 — 从静态管道到 Autonomous Agentic System（2026-04-04）

## 核心认知跃迁
> 当系统拥有了"求知欲(Curiosity)"和"反思能力(Reflexion)"，
> 它就不再是工具，而是智能体。

## 1) 升维一: Cron-Driven Autonomous Ontology（自组织知识网络）

### 从 v2.1 到 v3.0 的质变
```
v2.1 OOV Pipeline: 被动式 — 有JD进入才触发新词发现
v3.0 Autonomous:   主动式 — Celery Beat定时爬取+推理, 无需外部输入
```

### 学习要点
- **Continuous Knowledge Distillation**: 持续知识蒸馏，企业级系统的标配
  - 类比: Google Knowledge Graph 每天自动更新实体关系
  - 实现: Celery Beat (cron调度) + Google Search API / 招聘网站爬虫
- **高阶推理 vs 普通LLM**: 新词归类需要 CoT 级别推理能力
  - 普通LLM: "MCP协议是什么？" → 可能胡说
  - DeepSeek-R1/o1: 开启 `<think>` 模式, 逐步推导拓扑位置+前置技能链+替代关系
  - 输出不仅是分类, 还有**前置技能链**和**替代/演进关系** → 图谱拓扑更丰富
- **图谱边类型扩展**: v2.1只有 PROMOTION + LATERAL_TRANSFER
  - v3.0新增: PREREQUISITE (前置技能) / REPLACES (替代) / EVOLVES_TO (演进)
  - 这让图谱从"岗位路径图"进化为"技术演进知识图谱"
- **热度预测**: 每个新发现的技能附带6个月热度预测(高/中/低/昙花)
  - 避免在"昙花一现"的技术上浪费图谱空间

## 2) 升维二: Actor-Critic Reflexion Loop（审查智能体）

### 核心设计模式
```
单轨生成 (v2.1):  Planner → 输出  (无校验, 可能过度乐观)
对抗生成 (v3.0):  Planner → Critique → [REJECTED] → 重规划 → ... → 输出
```

### 学习要点
- **Reflexion Loop**: 来自 Shinn et al. 2023, LLM Agent 自我反思的经典范式
  - 核心: Agent生成 → 评估 → 反思 → 重试, 而非一次性输出
  - 最多3轮防止无限循环; 每轮驳回累积负约束
- **规则硬检 vs LLM软审 的分工**:
  - 硬检(不用LLM): 学历门槛、非对称转移概率 — 客观数据，LLM判断反而不稳定
  - 软审(用LLM): 市场趋势、竞争激烈度、时间可行性 — 需要主观判断
  - 这种"规则先行+LLM兜底"的模式在企业级系统中极为常见
- **Critic温度=0.2**: 审查者必须严谨确定, 不要"创造性"输出
  - Planner可以温度0.7(鼓励探索), Critic必须低温(严苛审查)
  - 这是 Constitutional AI 的经典设置
- **保守路径兜底**: 3轮仍驳回 → 说明该生条件限制大
  - 不是系统失败, 而是诚实告知"你的条件限制了选择范围"
  - 比假装推荐一条走不通的路更负责
- **透明性设计**: 展示"曾考虑但被排除的路径"
  - 用户看到系统认真思考过所有可能性 → 信任度大幅提升
  - 类似医生说"我们排除了X和Y后，建议Z" vs 直接说"建议Z"

## 3) 升维三: Asymmetric Transition Probability（非对称转移概率）

### 核心公式
```
P(Source → Target) = coverage(S,T) × exp(-λ × energy_barrier)

其中:
- coverage = |S∩T| / |T|  (非对称! 分母始终是Target)
- energy_barrier = Σ(weeks_i × difficulty_tier_i)  对所有缺失技能
- λ = 0.02  (衰减速率, 可调参)
- 博士级技能(tier≥5)额外惩罚×0.3
```

### 学习要点
- **对称性陷阱**: Jaccard = |A∩B| / |A∪B| 天然对称
  - 后端→前端 = 前端→后端, 这违背常识
  - 非对称的关键: 分母只用 Target 的技能集, 且加入获取成本
- **技能势能壁垒 (Energy Barrier)**: 受物理学启发的隐喻
  - 学 HTML = 1周×tier1 = 壁垒1 (几乎为零)
  - 学 CUDA优化 = 16周×tier5 = 壁垒80 (极高)
  - 指数衰减让高壁垒技能的影响被放大, 符合直觉
- **关键路径法估算转型时间**:
  - 不是简单求和(假设串行), 也不是取最大(假设全并行)
  - 实际 = max(最难技能时间, 总时间/并行度), 更接近现实
- **与 v2.1 的渐进兼容**: 数据充足时v3.0主导, 数据不足时回退v2.1
  - 这种"渐进式算法升级"在企业中极为重要 — 不能一刀切
- **论文级创新点**: "基于技能势能差的非对称职场跃迁算法"
  - 目前学术界的 job transition 研究多用对称相似度
  - 引入物理学势能壁垒 + 指数衰减 + 关键路径法 = 三合一创新

## 4) 三者的协同效应

```
升维一(知识) × 升维三(算法) × 升维二(审查) = 自进化闭环

1. 自组织知识网络 不断发现新技能 → 图谱节点增长
2. 非对称转移算法 精确计算每条路径的"势能壁垒" → 图谱边质量提升
3. Actor-Critic 审查 对规划结果做对抗性校验 → 最终输出务实可靠

三者形成正向飞轮:
  知识越丰富 → 算法计算越准 → 审查越有依据 → 用户信任越高 → 数据越多 → ...
```

# v3.1 对抗性审计修复 — 堵住 v3.0 三大工程盲区（2026-04-04）

## 核心认知: "优雅的公式不等于正确的系统"
> 再漂亮的 exp(-λ·barrier) 也拯救不了 Garbage In。
> 再精妙的 Reflexion Loop 也扛不住 30s 延迟。
> 再智能的 Cron Job 也挡不住 HR 写的 "Jave"。

## 1) 审计一: "数据真空"修复 — Quad-Source Calibration

### 核心问题
- v3.0 的 `SKILL_ACQUISITION_COST` 是硬编码常量
- 如果 weeks/difficulty 靠 LLM 脑补 → **GIGO (Garbage In, Garbage Out)**
- 不同人学习速度差异巨大, 单一来源不可靠

### 学习要点
- **加权中位数 vs 均值**: 均值受极端值影响大（培训班号称1周学深度学习）, 中位数天然抗噪
- **2σ离群检测**: 去除偏离中位数>2个标准差的估计, 统计学基础但极其有效
- **四源交叉验证**: 同一个技能从4个独立来源获取数据, 不同来源的偏差会互相抵消
  - GitHub Roadmaps (社区共识) + 培训大纲 (商业标准) + SO Survey (真实统计) + JD信号 (市场需求)
- **校准置信度**: `source_diversity × 0.5 + consistency × 0.5`
  - 来源越多+来源越一致 → 置信度越高
  - 低置信度 → uncertainty_penalty 放大壁垒 → **保守原则: 宁可高估壁垒, 不低估**
- **竞赛策略**: Source A (GitHub) + D (已有JD) 零成本, 覆盖核心50技能即可

## 2) 审计二: "灾难性延迟"修复 — Early Stopping + Negative Cache

### 核心问题
- v3.0 最坏情况: 3 × (Planner 3s + Critic 3s) = 18s (纯LLM串行)
- 叠加 L4 → 总延迟可能突破 30s-1min
- C端产品 >10s 用户流失率急剧上升

### 学习要点
- **Pre-flight 剪枝**: 在调用 Planner LLM 之前, 先用 O(1) 规则预检
  - 不可达节点提前裁剪 → Planner 搜索空间缩小
  - 这是经典的"规则先行, LLM兜底"模式 — 便宜的计算先做
- **Confidence-based Early Stopping**: 60%的用户条件好/路径明确
  - Planner confidence > 0.85 + 规则全通过 → 直接跳过 Critic LLM
  - 节省 1 次 LLM 调用 (3s), 对多数用户效果显著
  - 类比: 医生对明显的感冒不需要做全身CT
- **Negative Path Cache**: 缓存"死路"模式
  - 粒度: (source_category, target_category) 而非具体岗位ID → 命中率高
  - TTL=30天 (行业变化不会太快) + LRU淘汰 (max 500条)
  - 可从历史审查记录预热 (warm_up_from_history)
- **延迟预算思维**: 每个组件有固定延迟预算
  ```
  L0: 2s | L1: 0.5s | L2: 1s | L3: 4.8s | L4: 3-5s = 11-13s total
  ```
  - 企业级系统中, 延迟预算表是性能优化的基本工具
- **与 L4 Streaming 协同**: Reflexion 在后台运行时, 用户已经在看骨架报告
  - 用户感知延迟 ≈ 0s (骨架即时可见), 完整内容 8-10s

## 3) 审计三: "污染扩散"修复 — Quad-Layer Decontamination

### 核心问题
- HR 写 JD 的现实: 拼写错误 (Jave/ChatJPT), 概念混淆 (Excel=数据库), 噪声 (PPT)
- 脏数据进入图谱 → 通过边关系传播 → 污染扩散 (Contamination Propagation)

### 学习要点
- **SymSpell 拼写纠错**: 基于 BK-tree 的编辑距离算法, 100万词/秒
  - IT专用词典 + KNOWN_TYPOS 硬编码表 → 双保险
  - 类比: 搜索引擎的"您是否要搜索..."功能
- **OOD 异常检测 (Out-of-Distribution)**:
  - 核心思想: 如果一个词的 embedding 离所有已知技能都很远, 它大概率不是IT技能
  - θ_ood = 0.55 是 BGE-M3 的经验阈值
  - IT_CORE_CATEGORIES 白名单 → 非核心域直接 REJECT
- **隔离沙箱 (Quarantine Zone)**: 借鉴安全领域的"沙箱"概念
  - 影子模式: 新词参与计算但不影响最终得分 → 零风险观察
  - 14天观察期 = 2个 Cron 周期 → 足够积累统计数据
  - 晋升条件: 频次 ≥ 3% + 语境一致性 ≥ 0.8 → 双重保障
- **断路器 (Circuit Breaker)**: 借鉴微服务架构的熔断模式
  - 即使通过四层净化, 上线后仍持续监控
  - 匹配置信度下降 >10% → 自动回滚 + 告警
  - 最后一道防线: 承认"我们可能错了"并自动纠正

**日期**: 2026-04-05

### 学到了什么
- **智能体 = 向量存储 + 对话是必备**: 主题是"智能体"时，向量数据库(语义检索/RAG)和对话管理是刚需，不是可选项

  - **Neo4j**: 知识图谱专用，全量入图 (技能节点+岗位+晋升/换岗边+实体关系)，Cypher 路径查询极快

  - **Redis**: 会话缓存，竞赛级只需 session + 热查询缓存，不需要 Celery Broker 等重度用法

- **R-09 知识库导出**: Neo4j + Milvus → JSON 格式导出，满足竞赛本地知识库提交要求
- **竞赛级 vs 企业级**: 竞赛项目不需要 Celery Broker、分布式锁、限流等工程化组件，但核心数据架构不能偷工减料

## 8) ReAct Agent + Multi-Tool 智能体架构

**日期**: 2026-04-05

### 学到了什么
- **ReAct 框架**: Reasoning + Acting，LLM 先推理("我需要查图谱")再行动(调用 Neo4j Tool)，循环直到得出最终答案
- **Multi-Tool 设计**: 智能体不绑定单一数据源，而是拥有多个 Tool (Neo4j/MySQL/Milvus/Pipeline/LLM)，自主决定调用哪个

- **三层记忆架构**: 短期(Redis Session) + 长期(MySQL 持久化) + 语义(Milvus RAG) — 解决"对话遗忘"和"跨会话记忆"
- **6层架构**: L0-L4 管线是数据处理层，L5 ReAct Agent 是智能交互层，Agent 层统一调度所有下层能力
- **R-11 对齐**: "采用大模型为大脑并自主执行相应任务就是智能体" — ReAct + Tool 调度完美满足这个定义

## 9) MiroFish 开源项目参考 + 后端骨架搭建

**日期**: 2026-04-05

### 学到了什么

#### MiroFish 架构分析 (GitHub 3.5k+ stars, 盛大孵化)
- **纯 Python ReAct 实现**: MiroFish 不依赖 LangChain, 用纯 Python 实现 ReAct 循环 — 更轻量、更可控、更适合竞赛项目
- **Tool Call 解析**: 用 `<tool_call>{"name":"...", "parameters":{...}}</tool_call>` XML 标签格式, 比 LangChain Function Calling 更通用 (兼容所有 LLM), 还有裸 JSON 兜底解析
- **冲突处理**: LLM 同时输出 tool_call + Final Answer 时, 前2次拒绝要求重试, 第3次降级截断 — 这种容错机制是生产级必备
- **Flask 应用工厂模式**: `create_app()` + Blueprint 分层路由, 是 Flask 项目的标准架构模式
- **LLMClient 统一封装**: OpenAI SDK 格式统一调用, 支持 `chat()` + `chat_json()` + `<think>` 标签移除 + markdown 代码块清理
- **retry_with_backoff**: 指数退避重试装饰器, LLM API 调用必备 (jitter 随机抖动避免惊群)
- **JSONL 结构化日志**: Agent 每步动作写入 `agent_log.jsonl`, 方便调试和竞赛答辩演示
- **文件系统 JSON 持久化**: 竞赛级项目不需要复杂 ORM, 直接 JSON 文件 + dataclass 序列化够用

#### CPA-Agent 后端骨架设计
- **5 个 Blueprint 分层**: `/api/graph` (图谱) + `/api/profile` (画像) + `/api/match` (匹配) + `/api/report` (报告) + `/api/agent` (对话) — 比 MiroFish 的 3 个更细分
- **BaseTool 抽象基类**: `name/description/parameters/execute()` 四件套, 新增工具只需继承 BaseTool 实现 execute
- **AgentResponse 数据结构**: 包含 `reply` + `tool_calls` + `thinking_steps` + `elapsed_seconds`, 前端可展示完整推理过程
- **Tool 定义即文档**: 每个 Tool 的 description 直接注入 System Prompt, LLM 根据描述自主决定调用哪个 — 这是 MiroFish 的核心设计思想

#### 关键对比: MiroFish vs CPA-Agent
- MiroFish 无传统 DB (全靠 Zep Cloud + 文件系统), CPA-Agent 有四库分治 (Neo4j+MySQL+Milvus+Redis) — **我们的数据层更强**
- MiroFish 的 ReAct Agent 用于报告生成 + 对话, CPA-Agent 的用于**职业规划全流程** (解析→画像→匹配→报告→对话) — **我们的 Tool 覆盖面更广**
- MiroFish 的 Ontology Generator 由 LLM 动态生成实体类型, CPA-Agent 的 19 种实体 + 24 种关系已冻结 — **我们的 Schema 更成熟**

## 10) 四库存储 Schema 设计 — JSON Schema vs DB Schema

**日期**: 2026-04-05

### 学到了什么

#### 两层 Schema 的区别 (关键认知)
- **JSON Schema** = 数据合同 (对外, 定义数据长什么样) — 冻结后绝不改
- **DB Schema** = 存储设计 (对内, 定义数据怎么存) — 软冻结, 允许加列不允许改列
- 两者是独立的设计阶段, 不要混为一谈

#### Hybrid 模式 (MySQL 核心列 + JSON 列)
- **问题**: 冻结的 JSON Schema 嵌套深 (如 D1_basic.sub_degree), 完全范式化会产生 20+ 张表
- **解法**: 高频查询字段 (student_id, degree, competitiveness) 拆为独立列建索引; 完整结构化数据存 JSON 列
- **好处**: SQL JOIN/WHERE 用索引列, JSON_EXTRACT 查深层字段, 冻结 Schema 原样保留
- **企业中也常见**: MongoDB 的 BSON 模式, PostgreSQL 的 JSONB 列, MySQL 8.0 的 JSON 虚拟生成列索引

#### Neo4j 双图设计
- **Graph A (知识图谱)**: L1 构建, 确定性结构 (Skill/JobPortrait/CareerNode), 全局共享
- **Graph B (简历实体)**: L0 抽取, 每份简历独立, 19 实体+24 关系 → 按 student_id 隔离
- **为什么分离**: Graph A 是"世界知识" (所有用户共享), Graph B 是"个人数据" (每个学生独立)

#### Redis 滑动窗口 (对话上下文管理)
- `session:{id}:history` 用 LIST 类型, LPUSH 新消息 + LTRIM 保留最近 20 条
- 解决 "50 轮对话 token 超限" 问题: 只取最近 20 条 + Milvus RAG 语义检索补充远期记忆
- TTL 2h 自动过期, 活跃会话续期

#### career_report 6 章拆列
- ch1~ch6_json 独立 JSON 列, 而非一个大 report_json
- 支持 Phase 1 (模板直填, T=0s) 先写入 ch1/ch3/ch4/ch5/ch6, Phase 2 (LLM 并行) 后更新 content 字段
- SSE 推送时可以按章节粒度通知前端 "Ch1 已就绪"

#### Milvus conversation_vectors 跨会话 RAG
- 关键字段: `student_id` (不仅是 session_id) — 允许跨会话语义检索
- "之前我们聊过 Python 相关的内容吗" → 按 student_id 检索所有历史会话的对话向量
- 这是"语义记忆"层, 区别于 Redis 的"短期记忆"和 MySQL 的"长期记忆"
