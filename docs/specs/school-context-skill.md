# 院校背景上下文认知 Skill：有界设计与实现交接

**状态：**产品/能力设计，尚未接入运行链路；不是已上线功能说明
**日期：**2026-10-14
**上游产品目标：**[学生私人工作台体验任务](student-workbench-experience.md)第 5、6 节
**本任务边界：**只设计 Agent 可调用的院校背景解读能力；不修改 L0、D1 评分、管理员审核、前端或 Agent 拓扑。

## 1. 用户要解决的不是一个新的打分器

学生看到「本科、某地方本科院校、计算机科学与技术」时，希望 Agent **主动说出院校背景在常见求职语境里意味着什么**，而不是只复述学历与学校，或以「尚未管理员审核」拒绝做任何现实解读。Agent 如果不知道「双非、双一流、211、985」的常见含义，应能调用一份可维护的上下文认知能力，而不是临场凭模型记忆编学校名单。

Skill 只回答「怎样理解这个背景，以及当前依据允许说到哪一步」。它不决定学生价值、不修改画像分数、不代替某个岗位的招聘条件，也不把一般招聘印象写成全市场统计结论。

第一屏的落点是画像的**基础背景解读**，不是姓名旁的身份徽章。建议内容结构：

> 简历显示你是〔学校〕〔专业〕〔学历〕。〔经可识别来源确认的学校标签，或清楚标明的未知〕。在常见校招语境里，〔直接描述学校名称可能带来的识别优势或限制〕；看具体方向时，再结合项目、实习和岗位条件判断。

若已经有充分事实，应直说「这所学校通常不自带 985/211 的校名优势」，不以长篇免责声明掩盖判断；若学校身份本身还没识别清楚，也不能把猜测包装成该校的确定标签。

## 2. 四种不同性质的判断，不能揉成一句

| 层 | 可说什么 | 权威来源与禁止越界 |
|---|---|---|
| 学生资料事实 | 学历、学校原名、专业、校区或入学时间（若有） | 仅用当前 owner 的已确认简历/明确自述，保留原文与资料版本；简历写「本科」不自动证明「一本」。 |
| 院校标签事实 | 某校是否在某版 985、211、双一流名单，或资料确实无法识别 | 独立版本化的学校别名与名单知识；需要记录来源、适用版本、匹配方式。标签可并存，不以「最高档」抹掉其他事实；「双一流」还须注意学校与建设学科信息的差别。 |
| 社会/招聘语境 | 校名在部分筛选情境中的一般识别度，何时会让项目经历更重要 | 明确是常见印象和分析，不是教育主管部门结论、真实录用概率、对每家企业的断言；表述应具体但不过度防御。 |
| 某岗位的条件 | 指定岗位是否要求特定学校、学历、专业 | 必须有该岗位当前可信的条件原文及版本；不能仅凭一般印象说「你进不了某公司」。无岗位时保持一般情境分析。 |

**第五条边界：D1 正式分。**`school_tier_review`、已确认原文类别和现有 `PortraitGenerator` 的学校子分走独立业务门禁。Skill 的学校名单命中、通俗「双非」标签、模型措辞或用户自述都**不得写回** `semantic_facts.school_tier`、`school_tier_review`、`sub_school`、`dimension_score`，也不得把 D1 的 `partial` 偷换为 `completed`。这只是不让解释越权计分，不是要求普通社会解读先经过管理员审批。

术语处理：985/211 是历史建设工程标签；「双一流」按所用名单版本表述；「双非」是通俗简称，通常指非 985、非 211，**不能顺手推断必然非双一流**。本科是学历层次，不是学校工程类别。一本/二本涉及招生批次与时间、地区，不从「普通本科」或校名倒推。学校别名、独立学院、改名或校区不确定时先保留原名和未知，不做相似名硬匹配。

## 3. 何时调用、输入什么、返回什么

这是**同一主 Agent 的只读领域能力**，不是新增自治 subagent。触发建议：

1. 当前学生的已确认资料含有学校或学历，Agent 第一次形成/刷新基础背景解读时**主动调用**；不要求学生先问「我的学校如何」。资料版本或 Skill 知识版本变化后，缓存的解释失效，重新调用。
2. 用户主动问院校层次、校招筛选或某方向与学校背景的关系时按需调用；已有同版本结果可直接引用，避免每次重复查询。
3. 只有目标方向时，给方向相关的**条件式语境**；只有经核验的具体岗位条件时，才输出该岗位的确定门槛。无学校资料时不调用学校名分类，只对已知学历作有限解释。

最小输入应是服务端绑定的当前学生资源引用，而非让浏览器或模型提交任意 `student_id`、大段简历正文：

```text
profile_ref: 当前 owner 的已确认资料版本
school_name / degree / major: 从该版本服务端提取，原样保留
target_direction?: 用户明确选的方向；不是正式岗位
job_requirement_ref?: 已核验岗位条件版本；无则省略
knowledge_version: 本次学校知识快照版本
```

建议输出为结构化判读，再由 Agent 写产品文案；示意字段不是当前 API：

```json
{
  "status": "interpretable",
  "profile_version": "当前已确认资料版本",
  "knowledge_version": "学校知识快照版本",
  "school_identity": {"original": "原学校名", "matched_name": "核对后的学校名", "match_basis": "exact|verified_alias|unknown"},
  "institution_facts": [{"label": "211", "state": "yes|no|unknown", "source_ref": "版本化来源引用"}],
  "common_context": {"text": "对学校品牌信号的直接、条件化解读", "kind": "general_social_interpretation"},
  "job_condition": {"status": "not_provided|verified|unknown", "source_ref": null},
  "unresolved": ["仅列真正会改变这段解释的歧义"],
  "scoring_effect": "none"
}
```

名单不能覆盖全体学校时，「未命中」只能输出 `unknown`，不能输出 `no`。只有可证明完整、适用当前版本的名单，且学校身份已经精确匹配，才可据其缺席判断「非该名单」。Skill 不输出伪精确的学校排名、概率、学校质量分或 D1 分；`common_context` 不允许有未经验证的「市场热度」「所有大厂」「一定被刷」等表达。

## 4. 知识维护和接入路径（待实现会话核实）

**现有现场，不应误称已接入：**

- `backend/app/utils/skill_system.py` 有 Markdown Skill 发现、上下文生成和显式 executor 注册结构；仓库内搜索未见其被当前 Agent 主链调用。单放一个 `SKILL.md` 不会让学生页面获得能力。
- 主 Agent 实际工具经 `backend/app/services/langgraph_agent.py::_build_langchain_tools`、`agent_runtime/tool_factory.py` 与 `agent_runtime/tool_policy.py` 暴露；现有 profile/qa 提示词在 `backend/config/prompts/agent.profile.system/base.md`、`agent.qa.system/base.md`。如以工具形态接入，需走同一权限、工具事件与双通道输出，不直接往提示词塞一整份学校名单。
- 当前 L2 的 `backend/app/pipeline/entity_extractor/portrait_generator.py` 对学校计分依赖已确认语义事实或有效官方审核；`backend/app/services/school_tier_review.py` 是独立的人审评分输入。`docs/specs/school-tier-review.md` 所述 live 库未迁 `0005`，不是上下文 Skill 的上线前置条件，也不能被 Skill 绕过。
- `backend/config/defaults/rules/scoring_tables.yaml` 仍含一本/二本/三本等历史评分枚举，但抽取明确禁止按校名推断。Skill 不能借评分表冒充学校知识库；`workspace/seeds` 目前也不是 live 能力。

**推荐最小切片：**将「学校名单与别名事实」和「如何解释它们的 Skill 指南」分开版本化，作为只读领域资源由受控调用加载。优先复用当前主 Agent 的工具适配/权限/事件链，不另造一套技能执行编排器；若选择现有 `skill_system.py`，先补真实消费点与门禁，而不是仅注册目录。事实数据可按 985、211 历史名单及双一流**明确轮次**维护，记录来源 URL、抓取/核对日期、适用范围、完整性、别名审阅记录和内容摘要。官方名单可作标签事实来源；社会印象是 Skill 解释规则，不伪装成官方原文。参考教育部的 [211 工程学校名单](https://www.moe.gov.cn/srcsite/A22/s7065/200512/t20051223_82762.html)、[985/211 术语说明](https://www.moe.gov.cn/jyb_xwfb/xw_zt/moe_357/s7865/s7987/s7995/201404/t20140428_167741.html) 与 [第二轮双一流建设高校及学科名单](https://www.moe.gov.cn/srcsite/a22/s7065/202202/w020220214318455516037.pdf)；实现时须复核当前来源可用性和是否已有更新轮次，不能仅复制本页链接就算核验。

知识更新独立于学生资料更新；产物必须标记 `knowledge_version` 和 `profile_version`。旧解释可留在历史快照，但新版本出现时不能继续当作当前事实。Skill 不执行网络任意抓取、不写学生记录、不调用管理员审核 API。调用过程在只读过程栏逐条显示为「核对院校背景语境」＋实际 Skill/工具名，展开可看可展示的真实记录；事实来源和解读则出现在基础背景结论附近。

## 5. 参考输出和反例（用夹具验收，不代表具体学校已核对）

1. **已确认普通本科，知识快照确认非 985/211，未选岗位。**「你的本科专业是计算机科学与技术。这所学校在常见校招语境里通常不自带 985/211 的校名优势；相比只列技术词，更值得把你亲自完成的项目结果放到简历前面。」依据区列资料页、学校名单版本和「一般语境」标记。不说「双非学生竞争力低」或「无缘算法岗」。
2. **知识快照确认某校是 211 且在指定轮次双一流名单。**两项事实可并列；解释「这通常是校招初筛中较容易被识别的教育背景信号」，不自动说「985」，不把学校标签变成个人技能分。
3. **仅有学校名称，存在同名/改名歧义。**先显示学校原名和学历；学校名单判断为未知，可问一个能消歧的具体问题。不能把最相似的 985 校名套给学生，也不让整个画像因这一段解释失败而全空。
4. **学生选了 AI 应用开发方向，但没有可信岗位条件。**说该方向可能更看重哪些可展示经历时，要明确这是探索性建议；不能写「目前企业普遍要求 211」或推出岗位匹配百分比。
5. **有一条经核验岗位要求指定学历/学校条件。**把「该岗位原文条件」单列，链接岗位版本；再解释学生已知事实是否满足。不得把这一条岗位要求泛化为整个行业。
6. **学生简历明确写「双非」，但知识快照显示学校在双一流名单。**保留学生原文；指出通俗「双非」与双一流并非同一组标签，两者可以并存。若原文直接断言与可靠名单冲突，标记冲突待纠，不静默替换学生事实或 D1 审核结果。

## 6. 交给实现会话的验收门槛

- **入口与主动性：**通过真实 owner 资料→基础背景→Skill/工具调用→页面回读证明，不以「模型在聊天里知道 985」或孤立单测代替；非学生 owner 读不到私人资料。无学校事实时不制造标签。
- **事实与语境：**用 985、211、双一流、普通本科、通俗双非、同名歧义及名单未覆盖夹具验证事实/解释分开；名单版本和来源可回看；学校层次可以直说，但无法依据时不杜撰。
- **业务隔离：**同一简历运行前后比较 L0、审核表、D1 字段和正式画像状态；仅 Skill 解读变化不能使 `partial` 变 `completed`、填出 `sub_school` 或生成总分。目标产品未来若改画像完成语义，应由独立后端状态任务迁移，不归本 Skill 偷渡。
- **岗位边界：**无岗位、只有方向、已有核验岗位三种输入输出不同；无来源时无具体门槛、薪资、录用概率或「市场热门」断言。
- **版本和可观察性：**学校知识或学生资料版本变化后旧解读标旧，重新生成；过程栏能看到真实调用，失败/超时/知识不可用标未知且提供继续路径，不伪装已核对；学生界面只呈现可安全展示的数据。

本稿只依据文件与目标契约做接入点调查；**未运行后端/数据库/浏览器链路**。实现会话须先核对实际注册入口、当前服务与知识来源，再以真实链路验收。
